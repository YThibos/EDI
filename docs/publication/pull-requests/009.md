- I fixed the failing SonarQube quality gate: the PR's own code caused it, and the gate now passes when run locally the same way CI runs it. **What was wrong.** The CI log only said the gate failed, so I started the same SonarQube server version locally and ran the CI analysis against it (`ops/sonar-setup.sh`, then `./mvnw -Psonar verify ...:sonar`). The failing condition was the reliability rating, which came out at C where the gate requires A. Five issues caused it: - **Four possible-null warnings (java:S2259)** in `DispatchStore.countIn`, `EventCursorStore.positionOf` and `WorkKeySequenceStore.lastIssued` / `highestOnATask`. Each reads a single number with `.query(Integer.class)` or `.query(Long.class)`, then `.single()`, and returns it as a plain `int` or `long`. In Spring 7 that result is marked as possibly null, so Sonar reports a possible NullPointerException. - **One slow-regex warning (java:S8786)** in the test helper `StubJiraServer.found`: the pattern `.*project = "(...)".*` used with `replaceAll` can backtrack heavily. **The rule that must hold:** reading a single number from a store must never return a possibly-null boxed value as a plain `int` or `long`. **The fix.** - **Stores:** these reads now use the form the other stores already use and Sonar accepts (`InboxStore`, `NoticeStore`, `RecoveryCostStore`): `.query((row, _) -> row.getInt(1))` or `row.getLong(1)`, then `.single()`. I applied it to the four flagged reads and to every other read of the same shape that Sonar didn't flag: `TaskStore.contains`, `EventLog.record` and `EventLog.latestSequence`, and `DecisionStore`. The SQL is unchanged and each query still returns a non-null value (they use `coalesce`, `count(*)` or a key returned by an insert), so the results are the same. - **Test helper:** `StubJiraServer` now uses a fixed `PROJECT_CLAUSE` pattern with `find`. It fails loudly if a query has no project clause. My first attempt, `.optional().orElse(...)`, was still flagged, so I replaced it with the form above. **Verification.** Run locally against SonarQube 26.10 community with the CI gate setup: every test passed, the build succeeded, the quality gate passed, and no unresolved reliability issues remain. I removed the temporary container and temporary files afterwards. The changes are in the worktree and not committed (7 files under `edi-core`)
