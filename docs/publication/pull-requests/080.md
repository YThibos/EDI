# EDI-124 The shell secret guard matches paths, not the literal text of a word

## What it changes

The shell secret guard recognises a secret file by the path it resolves to, not by the literal text of a word, and covers the tools that bypass the shell.

The commits, in order:

- Read a captured log event without a message as an empty line
- Match a secret on the real paths a shell word leads to and guard a worker's Glob
- Record what the secret guard matches and what a denylist cannot contain
- Pin that a path built at run time and a link made in the same command pass the guard
- Read a shell word's paths as bash expands it and refuse what the guard cannot trace
- Mark the item delivered
- Read the commands inside an extended glob, so a negated subshell stays guarded
- Look up the path after a word's first = and after a curl @ mark
- Resolve real paths through one helper for the guard's reads, writes and searches
- Record the extended-glob commands and the prefixed paths the guard reads
- Keep the path matching to workers and read a glob group attached to a word as zsh does
- Refuse unreadable attached glob groups and read short-option paths
- Hand the item over to the cloud session on its pull request
- Write the open question and the findings left into the handover
- Read a group attached to a word as part of it even with a blank, refuse zsh qualifiers that run code, and look past bundled short options

## How it was verified

The repository's build and tests, `./mvnw verify`, passed before the merge, with the native build where the change could reach the native image, and CI ran on the pull request.
