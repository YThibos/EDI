## Goal

When a worker reports done, the core verifies its delivery, books its measured time and moves its ticket itself, and on the merge it moves the ticket on, books what was worked since and cleans up, so none of these checks or bookings depends on the primary remembering them, and no shell script remains in EDI's procedures.

## Context

In the week of 26 October 2026 the primary spent about 140 tool calls on this by hand: 77 merge-request state checks, 40 JIRA calls (worklogs, transitions, sprint), and 25 checks for SNAPSHOT versions and the worked line.
On 2 November it booked worked time at the wrong hour once (the worker's times were UTC), and a ticket stayed in To Do after its merge request was ready because a transition was refused.
EDI moves JIRA tickets through `JiraTracker.transition` and the workflow in the machine profile, but never books a worklog and never creates a story; the primary does both by hand with a shell script, the workaround behind learnings 8 and 26 of the first week, which expire with this item.
EDI-54 landed a domain `WorkedTime` that sums a task's active stretches, which `edi task show` prints and cleanup writes as a `task.worked` ledger record.
[EDI-94](EDI-94.md) (worklogs and stories through the tracker) described the same work from the stage's side; the captain folded it into this item on 3 November 2026, and [EDI-163](EDI-163.md) supplies the walk that moves a ticket to a named state.
The captain's JIRA flow: Test in DEV when a merge request is ready for his review, which means he tests it on his own machine; TEST in TST once merged into the project's main branch, which auto-deploys to the test server; Ready For Prd once tested; a ticket enters the current sprint when work starts; a later slice starting on a ticket already past In Progress moves it back there; evergreen tickets get worklogs only.
The research is in [the EDI-74 plan](research/EDI-74-plan.md), section 5.1 (lines 8 and 26) and step 24, and [the EDI-52 plan](research/EDI-52-plan.md), finding F3.

## Acceptance criteria

- On a ship's done the core checks, through the forge adapter: the request is open and not a draft, its head is the worker's head, its checks are green on that head, it is mergeable, and the branch adds no SNAPSHOT version; any failure goes back to the worker as a steer naming it, and the done is not accepted.
- The `Tracker` port gains booking a worklog and creating a story; the JIRA adapter implements both, and the EDI-native and no-tracker adapters refuse or do nothing as their kind says.
- At an accepted done the core books the task's active minutes so far, from `WorkedTime`, as one worklog on the task's ticket with a comment naming the work and the request; at cleanup it books only the active minutes worked after the done, such as fix rounds; each minute is booked once, and a second cleanup books nothing.
- A task keyed `EDI-n` books its minutes on the evergreen ticket the machine profile names (`tracker.evergreen.tooling`), with the EDI key in the worklog comment.
- The ticket's status follows the stored stage, through EDI-163's walk: READY moves it to the project's "ready for review" state and adds it to the current sprint; a merge into the project's main branch moves it to the project's "merged" state; a later slice starting on a ticket already past In Progress moves it back there; evergreen tickets are never transitioned.
- A ticket proposal answered yes creates the story through the port.
- The states and their transition paths come from the machine profile's tracker workflow, read at the moment of use, not from code.
- Each step is recorded in the task's timeline, and a failed tracker call becomes a blocker in the turn report, never a silent skip.
- No `jira-sync.sh` call remains in EDI's skills, briefs or procedures.
- `docs/decisions/trackers-and-time-booking.md` states the status flow and the booking rule, with a history line.
- Tests cover a clean done, each refused done, the booking at done and the later booking at cleanup, a second cleanup that books nothing, an `EDI-n` task on the evergreen ticket, each transition, an evergreen ticket, a story from an answered proposal and a failed tracker call.

## Requirements from decisions and answers

- Soft and silent failures are covered by hard rules that are non-negotiable and non-bypassable.
- Worklog amounts are the task's real active minutes, measured by the core, never rounded, invented or read from the worker's own report (the captain, 3 November 2026).
- The captain's JIRA status flow, followed strictly whenever EDI manages the JIRA side of tasks, driven from the task's stage and never by hand; stories never sit in Done before production.
- The transition names and numbers are in the machine profile's workflow, not in code; the captain's machine profile is not in the repository, so the tests run on a fixture profile and a stub, and the pull request says so.
- Secrets are read at call time by an adapter and never printed, logged or stored (I-32).
- The port count stays at six: the operations go on the existing `Tracker` port.
- Tracked files name no particular employer, host or ticket prefix: use invented names in tests and records.

## How to verify

- `./mvnw verify`, then the native quick build and its smoke test; the core's tests run under both the laptop and desktop fixture profiles, so a booking must happen on the first and not on the second.
- Tests with a stubbed JIRA over the adapter's HTTP boundary, as the existing adapter tests do.
- By hand on a test project with a stub forge and tracker: a done is refused for a draft request and accepted for a ready one, which books its time and moves its ticket; a merge moves it on and books what was worked since.
