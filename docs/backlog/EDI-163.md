## Goal

The primary moves a ticket to a target state with one call, the core finding the transition path, and can list tickets whose state disagrees with what has landed in the repository.

## Context

On 2 November 2026 the primary set a registered project's JIRA right by hand: about 40 chained transitions (a Done story to Ready For Prd takes nine steps), and a sweep reading every ticket's status and comparing it with commits on master.
JIRA's workflow offers no direct moves between distant states, so every move is a path.

## Acceptance criteria

- `edi tracker walk <KEY> "<state>"` finds the shortest path through the project's workflow (read from the tracker's transitions, cached) and applies it, stopping with the path taken if a step fails.
- `edi tracker drift <project>` lists tickets whose state disagrees with the repository: work merged but the ticket before its merged state, stories in Done before production, tickets in a review state with no open request, and tickets with no commit in an implemented state.
- Both go through the tracker adapter and its credentials, never through a hand-made call; on a project that carries its own JIRA script, they may reuse it by extending it, as that project's own rules require.
- Tests cover a multi-step walk, a failing step, and each drift kind.

## Requirements from decisions and answers

- No acceptance environment: a story tested on TEST goes to Ready For Prd; stories and bugs never sit in Done before production.
- Soft and silent failures are covered by hard rules that are non-negotiable and non-bypassable.
