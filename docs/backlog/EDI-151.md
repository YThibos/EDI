## Goal

`edi worker stop` leaves nothing running in the worker's isolated copy, so `edi worker relaunch` never has to wait on, or be refused by, a process the worker started and orphaned.

## Context

On 29 October 2026 a worker had started a front-end dev server (`npm exec ng serve` with its esbuild and sass children) for an end-to-end run.
The process that started it had exited, so the server was re-parented to the init process and kept running for 90 minutes.
`edi worker stop` signalled the worker's own process tree, which no longer contained the server, and the relaunch was refused: "a worker is relaunched only in a copy nothing else holds", naming the five process ids.
The primary had to find and end them by hand before the relaunch went through.
The relaunch refusal is right; the stop is what leaves the copy held.

## Acceptance criteria

- `edi worker stop <task>` also ends every process whose working directory or executable lies inside the task's isolated copy, after the worker's own tree, with the same signal-then-kill timing, and reports each one it ended.
- It never signals a process outside the copy, a process of another task, or one EDI cannot attribute to the copy (the I-30 rule: only processes EDI can name).
- A worker launched for the copy afterwards finds it free; the relaunch refusal stays for anything still alive.
- A test starts an orphaned child inside a fixture copy (re-parented by a double fork), stops the worker, and asserts the child is gone and a process outside the copy is untouched.

## Requirements from decisions and answers

- Never signal a process by name pattern; only process ids EDI has attributed to the task (I-30).
- The relaunch keeps refusing a copy that something else holds.
