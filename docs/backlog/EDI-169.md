## Goal

The publish guard's secret scan finds every secret gitleaks' standard rules recognise, wherever the secret falls in the outgoing commits.

## Context

While making CI green again (EDI-168, [pull request 191](https://github.com/YThibos/EDI/pull/191)), `SyntheticSecretsTest` failed on a CI run: gitleaks 8.30.1 found 4999 of 5000 generated AWS access keys committed in one file.
Reproduced in a cloud session with the pinned gitleaks 8.30.1:

- `gitleaks git` over one commit adding a file of 5000 keys, one per line (`cloud.key=AKIA...`, about 155 KB), missed one key in 2 of 400 trials; the two misses came while another heavy build ran, and none in 270 quiet trials, so load may play a part;
- the same keys spread over 50 files of 100 keys each still missed one key once in 100 trials, under load;
- `gitleaks dir` over one file of 100,000 such keys missed 43, at regular intervals of 925 lines (28,675 bytes) from line 9582 on, the first at byte 297,011;
- each key missed in that scan is recognised when the missed keys are scanned on their own, so the miss depends on where a key falls in gitleaks' input, not on the key.

The guard runs gitleaks through `Gitleaks.secretsIn` with `gitleaks git` over a push's outgoing range, and with `gitleaks dir` over a request's title and description, so a real secret in a large diff, or in a long description, can pass unseen.
EDI-168 makes `SyntheticSecretsTest` rescan a missed key on its own, which keeps that test about the generator, and leaves the guard as it is.
Severity: low, since a miss needs a large input and a rare position, but it is silent.

## Acceptance criteria

- A failing test first shows the guard missing a secret that gitleaks recognises on its own, at a position the reproduction names, in a push and, if it also misses there, in a request text.
- The cause is named: gitleaks' chunked reading, a race in its concurrent detection, or both, with the evidence; check gitleaks' own issues and releases for a known fault and a fixed version.
- The guard finds every such secret: by a gitleaks version that fixes it, by scanning the outgoing changes in pieces no larger than gitleaks reads whole, or by another means the reproduction supports.
- The test runs in a few seconds, skips with a reason when gitleaks is missing, and fails without the fix in every run, not in some.
- [publish-guard](../decisions/publish-guard.md) records the cause, the fix and what it still cannot contain, with a history line.

## Requirements from decisions and answers

- The captain (3 November 2026) asked for the miss to be its own backlog item, not part of EDI-168.
- Reproduce first with a failing test that shows the weakness, then fix it, then record the design in `docs/decisions`.
- The guard keeps gitleaks' standard rules only, which a repository cannot weaken ([publish-guard](../decisions/publish-guard.md)).
- A fix that changes how the guard scans, rather than only the gitleaks version, is asked on the item's issue with lettered options before any code.
- Tests and records use generated secrets and invented values only (`SyntheticSecrets`).
