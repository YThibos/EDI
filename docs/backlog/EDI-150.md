## Goal

No pull request or merge request title, description or comment that EDI or its validation pipeline posts on a forge carries a secret or personal material, so EDI-132's cleaning stays done.

## Context

The publish guard checks every outgoing commit: its added lines, paths, messages and identities ([publish-guard](../decisions/publish-guard.md)).
It never sees the text of a pull request.
The review of 29 October 2026 found that 17 of the repository's 87 pull request descriptions carried an internal proxy address and port, internal hostnames, the captain's work username, home paths, source-control group and project names and work ticket keys, while every commit passed the guard.
Those texts are written by the validation pipeline (the intent, the test evidence and transcripts it pastes) and by EDI's own delivery (`edi deliver`, worker reports turned into descriptions), and both quote the captain's words and local command output freely.
The captain decided on 29 October 2026 that the descriptions listing IP addresses and hostnames are critical, and that all descriptions are to be cleaned ([EDI-132](EDI-132.md)); without a guard, the next pull request brings the traces back.

## Acceptance criteria

- Every path by which EDI posts or edits a pull request or merge request title, description or comment on a forge runs the text through the same checks as a commit: the secret scan, the captain's deny-list and the personal-path check, sparing only the pushing project's own names as the guard already does.
- A refused text is not posted; the refusal names the place (title, description, line) and the deny-list entry, never the matched value, and tells the worker to rewrite it.
- The validation pipeline's own posting is covered too: while the pipeline is external, its descriptions are checked before EDI marks a request ready, and a failing description blocks the ready step with the same refusal; once EDI's own Publish slice ([EDI-147](EDI-147.md)) lands, the check sits in that slice's posting path.
- IP addresses outside the documentation ranges, and host:port pairs, are refused in these texts even when the deny-list does not name them.
- Tests prove each posting path refuses a text carrying an invented deny-listed term, an invented secret generated at run time, a home path and a private IP address, and accepts a clean text; the tracked tests carry nothing personal.
- The decision is recorded in [publish-guard](../decisions/publish-guard.md).

## Requirements from decisions and answers

- The captain (29 October 2026): the pull request descriptions listing IP addresses and hostnames are critical and must be fixed, and in fact all the pull request descriptions.
- A finding names its place, never the matched value ([publish-guard](../decisions/publish-guard.md)).
- Tracked files name no particular person, employer, account, host or machine path ([machine-and-person-specifics](../decisions/machine-and-person-specifics.md)).
