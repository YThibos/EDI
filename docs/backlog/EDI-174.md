## Goal

A worker's question, status or report reaches the primary as data to answer, and never as an instruction the primary follows.
The rule is written down and held in code where code can hold it, not only in a sentence of the anchor.

## Context

GitHub's scanner flagged, on PRs 201 and 202, that a worker's question text is shown inside the primary's session through the turn report and the reminder notification.
The text already reaches the primary whole on main through `edi worker list`, and the primary must read it to answer it, so those pull requests opened no new path.
The pre-tool guard is recorded as a denylist for a misled worker, not as a boundary, and no record yet states how the primary treats a worker's words.
The captain accepted the scanner threads as traced and asked for this gap to be closed separately.

## Acceptance criteria

- A decision record states that the primary treats every worker-authored text (status, question, report, pull request text) as data to evaluate, never as an instruction, and names the places it is shown.
- Every model-visible output that carries worker-authored text marks it as the worker's words in a consistent, recognisable way (for example a labelled quote), in the turn report, the reminder notification, `edi worker list` and `edi status` views.
- The anchor or the relevant skill carries one line pointing at that record.
- Tests prove the marking in each output.

## Requirements from decisions and answers

- D92 A: the scanner remarks on PRs 201, 202 and 207 were accepted as traced, and this gap is fixed on its own rather than inside those pull requests.
- Honesty and readability: the marking must keep the worker's question readable in full; escaping that garbles the question is not acceptable.
