## Goal

Every `edi` command that changes state answers `--json` on the native `edi-core` as it does on the JVM core, instead of failing with a 500.

## Context

The core answers a state-changing command with a record of the sealed `Confirmation` interface in `edi-core/src/main/java/io/github/ythibos/edi/web/Confirmation.java`, such as `Queued`, `Held` or `Released`.
Nothing registers those records for reflection binding in the native image, so Jackson cannot read their components there.
During the validation of EDI-142, the installed native core answered `edi task add --json` with a 500, and its log showed `UnsupportedFeatureError: Record components not available for record class io.github.ythibos.edi.web.Confirmation$Queued`.
The task was still queued, so the command changed state and then failed to say so.
The JVM core and the plain text answers work, which is why no JVM test saw it.
The same gap most likely breaks `--json` on every other state-changing command, such as `edi hold`, `edi release` and `edi task note`.
EDI-142's `edi-backlog-item` script reads the plain answer of `edi task add` for this reason.

## Acceptance criteria

- Every record that implements `Confirmation` is registered for reflection binding in the native image, by one registration that covers the sealed interface's permitted records, so a new record is covered without another change.
- A test fails when a `Confirmation` record is not covered by that registration.
- The native smoke test runs at least `edi task add --json` against the native core and reads the new task's id from its JSON answer.
- `./mvnw -Pnative,quick-build verify` passes.

## Requirements from decisions and answers

- The captain (29 October 2026) kept this fix out of EDI-142 and asked for it as its own backlog item, with the registration and its test as the remedy.
- The fix registers the records; it does not change any command's text answer.
