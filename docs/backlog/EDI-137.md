## Goal

A report that recommends how workers are kept from the captain's secrets by permission rather than by a denylist, compares a separate operating-system user with Docker Sandbox's token substitution, and ends in a sliced plan the captain can choose from.

## Context

Workers run as the same operating-system user as the captain's primary session.
The guards that keep them from the core token, the keys file, the EDI home and the captain's tmux server are denylists over the commands a worker runs, and a denylist cannot contain an agent running as the same user.
EDI-122, EDI-123 and EDI-124 each closed some ways around those guards and each left gaps, such as `exec -c`, `tmux new-window`, and paths built at run time, as with `python3 -c`; EDI-138 lists the bypasses found after they landed.
In D64 the captain chose option A: workers run so that the core token, the keys file, the EDI home and the captain's tmux server are out of their reach by permission.
With that answer, the captain asked for Docker Sandbox to be investigated as a fix as well.
Docker Sandbox, Docker's sandboxes for coding agents, gives the session a fake token; when the session makes a call, Docker intercepts it and swaps in the real credential, so the agent never sees it.
This item is that investigation; it was not started on the captain's machine.

## Acceptance criteria

- The report compares at least two options:
  - A: workers as a separate operating-system user, with what it takes: the second user, isolated copies shared through a group, and the changes to the install;
  - Docker Sandbox's token substitution: the session holds a fake token and an intercepting proxy swaps in the real credential at the call.
- For each option the report says how it fits Claude Code workers: the model provider's sign-in, git push credentials, the issue tracker and code host tokens (JIRA, GitLab, GitHub), and the EDI core token.
- For each option the report says whether it runs on WSL2, what it costs in performance, and how the worker still reaches the core, its isolated copy and its tmux window.
- For each option the report says what it still leaves within a worker's reach.
- Every claim about Docker Sandbox rests on a cited source of Docker's, read on the day, and says plainly what could not be checked from the sandbox.
- The report ends in one recommendation and a plan cut into slices, each a ship that can be backlogged on its own.
- The decisions the captain must take are laid out as questions with lettered options and a recommendation, each option on its own line, so his primary session can put them to him on a board.
- The report is delivered as a pull request on a `research/` branch, and changes no code.

## Requirements from decisions and answers

- D64, option A (the captain, 28 October 2026): workers must not be able to reach the core token, the keys file, the EDI home or the captain's tmux server, by permission and not by a denylist.
- The captain (28 October 2026) asked for Docker Sandbox, where a session works with a fake token and Docker replaces it with the real one at the call, to be noted down and investigated as a fix.
- The outcome is a recommendation with a sliced plan for the captain to choose from; the session does not choose for him.
- A guard is a denylist, not a boundary; the report does not claim more for an option than it gives.
- Tracked files and the report name no particular person, host, account or machine path; use invented values.
