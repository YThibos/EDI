## Goal

EDI records a validation of a task's head in its own store and runs the project's verify commands on it in a pinned worktree, beside the no-mistakes pipeline and without replacing it, so the rest of EDI's own validation pipeline has its record, its evidence and its restart safety to build on.

## Context

EDI drives the external no-mistakes pipeline today, and every failure measured from 21 to 27 October 2026 came from a part of it EDI does not need or already does better: 13 of 93 runs failed (9 on usage limits, 4 on daemon crashes), a rebase followed by a failed fix agent stranded two ships for 2 hours 31 minutes each, and the test step, which on EDI reruns the verify command the worker already ran, is 45% of the pipeline's tokens.
The captain chose to build EDI's own validation pipeline in six slices (D47 A); this is the first.
It builds the domain, the store and the first stage only, and changes no brief: a worker may run it beside no-mistakes, which stays the pipeline of record until slice 6.
The design is in [the EDI-105 research](research/EDI-105-validation-pipeline.md), sections "The design" and "Migration plan", as revised by EDI-105 on the stored task stage (EDI-85).

## Acceptance criteria

- `domain/validation` holds `Validation` (a task, a head commit, its base commit, the intent it is judged against, its stages in order and an outcome: running, awaiting the worker, awaiting the captain, passed, failed or superseded), `ValidationStage` and `Finding` (severity, file and line where it has one, description, and an action: `fix`, `ask-captain` or `note`), free of Spring and processes as `ArchitectureRulesTest` requires.
- A Flyway migration adds `validation`, `validation_stage` and `validation_finding`, and the events `ValidationStarted`, `StageFinished`, `FindingsRaised`, `ValidationPassed` and `ValidationFailed` are recorded and shown on the task's timeline.
- `edi validate`, run by a worker in its isolated copy, starts a validation of the copy's head and returns at once; `edi validation status` prints the stages, their state and their evidence.
- The `Verify` stage runs the project's verify commands through `ProjectBuild` in a detached worktree pinned at the head commit, and stores each command's exit, duration and log path as evidence; it adds the native quick build when the change can reach the native image, as `NativeImageInput` decides, and `edi publish-check`.
- Stopping the core in the middle of `Verify` and starting it again finishes the stage from its record without a second build (a test with the `Clock` port and a recording `ProjectBuild`).
- Two validations on the same machine run their verify commands one after the other, never side by side.
- A validation whose head does not descend from the previous validation's head on the same task is refused, naming each commit it would drop.
- Starting and ending a validation are triggers of the stored task stage as EDI-85 and EDI-86 define them (a running validation is CHANGING), never a second state beside it.
- No brief changes, `PortInventoryTest` and `ArchitectureRulesTest` pass unchanged, and the worker's result arrives as one inbox message.

## Requirements from decisions and answers

- D47 A (the captain, 29 October 2026): build EDI's own validation pipeline in six slices, cut over one project at a time after a shadow period.
- Q3 A: `Verify` runs the project's verify commands everywhere; an end-to-end agent is added in slice 6, only on projects that opt in.
- EDI validates its own changes with no-mistakes until slice 6 cuts EDI over, so a broken validation of EDI's own can never approve its own fix.
- No code path rewrites history: no rebase, no amend of a submitted commit, no force-push.
- No seventh port ([ports-and-architecture-rules](../decisions/ports-and-architecture-rules.md)): verify commands run through the concrete `ProjectBuild`.

## Research and measurements

- The test step: 131 calls, 107.3M weighted tokens (45%), 22.7 agent hours over 93 runs; on EDI a median 15.1 minutes against 3 to 5 minutes for the verify command alone.
- Failure modes 1, 2 and 5 of the research motivate the store-held record and the restart test.

## How to verify

- `./mvnw verify`, and `./mvnw -Pnative,quick-build verify`, since the change adds store tables and commands the native image carries.
- The restart test, the ordering test for two validations, and the refusal test for a head that drops a commit.
- By hand on a scratch project: `edi validate` in a copy, then `edi validation status` shows `Verify` passed with its log path.
