## Goal

Once a validation's review and verify pass, EDI pushes the head to the project's registered repository on the project's bound account and opens the draft with the verify evidence in its body, so no push ever goes out under whichever account happens to be active.

## Context

The no-mistakes daemon pushes from its own mirror with `gh auth git-credential`, which answers with the active `gh` account, so EDI's per-call account binding does not cover the pipeline's pushes ([no-mistakes verification notes](../verification/no-mistakes.md), account binding); `edi deliver` exists for the drafts the pipeline could not open.
EDI already binds each isolated copy's transport to a repository-local credential helper and refuses a push to any repository but the registered one ([forge-adapters](../decisions/forge-adapters.md)).
This item adds the `Publish` stage on slice 3, the item filed from `slice-3.md`, which must have merged first.

## Before starting

- Slice 3 has merged, and EDI-70 has merged, since the head this stage records is the delivered head landing compares with.

## Acceptance criteria

- `Git` gains a push of the validated head to the branch on the registered remote that goes through the copy's credential helper, refuses `--force` and any target `PublicationTargets` refuses.
- The push uses the bound account whatever `gh` account is active (a test with two recorded accounts).
- A push to any repository other than the registered one is refused (AT-43 extended), and no allow-list entry or argument carries `--force` (AT-03b extended).
- `DeliverDraft` becomes the `Publish` stage: it opens the draft through `Forge.openDraft`, titled with the work key and the task's title, and its body lists each verify command of the validation with its result.
- The pushed head is recorded as the task's delivered head, as EDI-85, EDI-86 and EDI-70 define it.
- `edi deliver` still opens a draft by hand for a task whose validation did not publish.

## Requirements from decisions and answers

- D47 A (the captain, 29 October 2026): EDI's own pipeline publishes, so pushes follow the account binding.
- Every request opens as a draft, and only the captain merges (I-03, I-04); EDI has no merge capability.
- D13 B: while CI does not run, the request's body carries the local verification.
