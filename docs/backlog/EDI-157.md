## Goal

The report says "hold the merge" only when something really moves under a merge request, never because the validation pipeline is still watching a request that is already ready.

## Context

On 2 November 2026 three ready merge requests (two SAP slices and a test tool) were shown as "Changing, hold the merge (pipeline ci)" for over an hour, because no-mistakes keeps its CI step running to watch a request until it is merged, after it has marked the run CI-ready.
The captain merged one of them believing the warning was noise; it was, but a true warning must never be trained away.
EDI-86 makes a request READY only from the forge's own view, which probably cures this, but does not say so.

## Acceptance criteria

- A request whose pipeline run has reached CI-ready (no-mistakes' `ci_ready_at`, or the equivalent stage of EDI's own validation once EDI-105 lands) and whose head equals the forge's head with green checks reads as READY, not CHANGING, while the pipeline only watches it.
- CHANGING still shows for a new commit, a running fix round, an unacknowledged steer, a worker back at work, or checks not yet green on the head.
- The reason shown with CHANGING names what moves, never only a pipeline step's name.
- Tests cover a watched ready request (READY), each true CHANGING cause, and the reason text.

## Requirements from decisions and answers

- Soft and silent failures are covered by hard rules that are non-negotiable and non-bypassable; a warning that is often false is itself a silent failure.
- Captain-facing text speaks in outcomes, never in internal labels such as a pipeline step's name.
