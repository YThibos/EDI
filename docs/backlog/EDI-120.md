## Goal

`WaitControllerTest` no longer races its own wake, and the production code is checked for the same race.

## Context

After the core moved to virtual threads (EDI-115), the captain's update run failed `WaitControllerTest.holdsAWaitOpenUntilAWorkerWakesThePrimary` under the desktop fixture profile, while the same test passed under the default profile of the same build.
The failing assertion checks that a request is still waiting right after the status that wakes it was recorded, which races the wake: when the wake is fast, no request waits any more.

## Acceptance criteria

- The failure is reproduced first, by running the test repeatedly and under load.
- The test is made deterministic without weakening what it proves: that the wait is held until the worker's status, then answered with the wake text.
- Production code is checked for the same race, a wake arriving between registering a wait and checking it, and fixed if it has it, with a test that pins the fix.
- The test is run at least 50 times, in both surefire profiles, and the results are in the pull request body.

## Requirements from decisions and answers

- A flaky test is fixed, never retried away.
- Time comes from the `Clock` port; a test that waits for real work waits on its event up to `Patience.FOR_REAL_WORK` and never asserts how soon it came ([AGENTS.md](../../AGENTS.md)).
- Offline verification: the local verify, both surefire profiles, the repeated runs and the publish check.
