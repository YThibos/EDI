## Goal

A public, read-only mirror of EDI's `main` exists and follows `main` automatically after every landing, with the right security settings and no personal or work-project material.

## Context

The captain asked for a new mirror repository with the correct security settings, updated automatically whenever something lands on the private repository.
A review on 28 October 2026 found that the private repository's code and full git history hold no secrets (scanned over every reference) and no employer or personal details in files or commit messages, apart from example work keys of a registered project in one test and one verification note, and a few early commits whose author address is personal.
Its pull request descriptions, Actions logs and artefacts do leak work-project details, so the private repository stays private and a new public repository mirrors `main` only.
GitHub Actions does not run on the private repository (billing limit); Actions on a public repository are free.
EDI's own rules forbid it to push to a base branch.

## Held on

This item is held on three decisions the captain has yet to answer, each put to him as a card, and on the security items.
The decisions are restated below as open questions; a cloud session does not decide them.

- D59, how `main` reaches the public repository after every landing:
  - A. A scheduled workflow in the public repository, for example hourly, fetches the private `main` with a fine-grained read-only token for that one repository, runs the secret scanner and the denylist, and fast-forwards the public `main`.
  - B. EDI's core pushes the private `main` to the public repository right after it records the captain's merge, under a narrow, recorded exception to the no-push-to-main rule for this one mirror.
  - C. No automation: the captain pushes to the mirror himself, with a one-line command kept ready.
  - Recommended: A, because it is free, runs without the captain's machine, leaves the no-push rule intact, and the token can only read that one private repository.
- D60, which licence:
  - A. Apache-2.0: permissive, with an explicit patent grant; common for Java and Spring projects.
  - B. MIT: permissive and shortest, no patent clause.
  - C. No licence: visible, all rights reserved.
  - D. AGPL-3.0: anyone who runs a modified EDI as a service must publish their changes.
  - Recommended: A, because it matches the ecosystem EDI is built on and the patent grant protects contributors.
- D61, how history is published:
  - A. The full history of `main`, as it is: an exact copy, and every later landing follows as the same commits.
  - B. One snapshot commit of today's `main`, then every later landing replayed as one commit each: no personal author address, but the mirror's commits differ from the private ones.
  - Recommended: A, because an exact mirror is simplest to keep in sync and to verify.
- Rewriting history is never done on the private repository.

## Acceptance criteria

- The new public repository, on the captain's personal account, holds `main` only, with no pull request history.
- Secret scanning with push protection, dependency alerts, private vulnerability reporting and a `SECURITY.md` are on.
- Actions default to a read-only token, approval is required for first-time contributors' workflows, and every action is pinned to a commit SHA.
- Branch protection on `main` allows only the sync's pushes, no force pushes and no deletion; the wiki and projects are off.
- The README says the repository is a read-only mirror and where to report issues.
- Every change that lands on the private `main` reaches the public `main` after the publish check (the secret scanner plus the denylist) passes on exactly what is pushed; a failing check stops the sync and tells the captain, and never pushes.
- The example work keys that name a registered project's ticket prefix in the branch-name test and in the verification notes are renamed to neutral keys before anything is published.
- The chosen licence is added.

## Not for a cloud session

Creating a repository, branch protection, secret scanning settings and a fine-grained token on the captain's personal account need that account and, for the sync's token, a secret that must never pass through a cloud session.
The workflow file and the denylist wiring can be prepared in a pull request, but the account steps are the captain's.
The item is listed as needs-captain-machine and held until his word on D59, D60 and D61.
